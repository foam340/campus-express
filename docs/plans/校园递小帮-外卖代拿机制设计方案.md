# 校园递小帮 · 外卖代拿机制设计方案

> 更新日期：2026-10-28
> 状态：需求整理稿；已确认规则与待定参数分开记录，尚未进入开发。
> 用途：供项目负责人及后续开发者继续讨论、确认和实施。本文不含密钥、生产访问参数或真实用户资料。

## 1. 功能目标与范围

在现有“快递代拿”之外增加“外卖代拿”，优先复用校园骑手、宿舍地址、支付、配送、客服、售后和钱包提现流程。

本方案暂按“外卖已到达指定取餐点，校园骑手再代拿送至宿舍”的场景设计。华师南海已确认5个取餐选项：北门（校内）、东南门（校内）、阳光（校外）、您宿舍楼下、商业街（校内）。北门、东南门、阳光和商业街为固定点位，“您宿舍楼下”需关联用户宿舍地址。各点的具体取餐方式如有特殊要求，再据实际情况补充，不默认扩大服务范围。

平台处理的是代拿配送服务费，餐费仍由用户在原外卖平台或商家处支付。

## 2. 负责人已确认的规则

| 项目 | 已确认决定 |
|---|---|
| 试行校区 | 目前仅华师南海校区，标识为 `nanhai`；华师石牌、广轻工暂不开放外卖代拿 |
| 数量 | 默认一单代拿一份外卖，不设置数量输入 |
| 尺寸 | 不设置小件、中件、大件等尺寸选项，不再将尺寸列为讨论事项 |
| 大单加价 | 不设置，不新增相关字段或操作 |
| 用户取消 | 未接单沿用现有取消流程；已接单后用户不能自行取消，须联系客服协商 |
| 待接单超时 | 不增加“超过送达截止时间自动取消、自动退款”的机制 |
| 超时提醒 | 不能直接照搬现有快递很急单提醒；是否需要及如何提醒，另行设计 |
| 新单通知骑手 | 有新的可接外卖订单时，发邮件通知骑手；外卖使用独立标题和正文，与快递通知内容区分 |
| 价格与送达时限 | 待负责人和其他人员商讨后提供，不预设金额、分钟数或计时起点 |
| 取餐地点 | 华师南海共5个：北门（校内）、东南门（校内）、阳光（校外）、您宿舍楼下、商业街（校内） |
| 其他流程 | 尽量与现有快递代拿一致，保留审核模式既有文字和操作 |

“一份外卖”是一次代拿任务，不要求用户另外填几袋、几盒或餐品明细。普通备注可以保留为选填，不承担数量或尺寸计价功能。

## 3. 尚待确定的参数

以下内容未获确认，不能将举例或技术建议当作最终规则：

| 待定项 | 需要提供或确认的内容 |
|---|---|
| 取餐点细节 | 固定点位名称和校内外归属已确认；“您宿舍楼下”的具体楼栋显示、交接位置及与配送位置的组合需核对，各点取放方式、柜号等按实际补充 |
| 收费 | 每单收费方式及金额，楼下与门口是否有差价，是否存在其他明确收费项 |
| 送达时限 | 目标时间、是否分档、从下单还是接单等哪个节点计时；支付和转单是否影响计时需明确 |
| 营业时段 | 每天何时接受外卖代拿订单，是否区分午晚餐，是否在20:00后继续开放 |
| 优惠及收入规则 | 是否使用现有优惠券、是否参与满减、是否沿用现有南海抽成口径，随收费方案确认 |
| 超时提示 | 首版是否需要提醒、触发条件、提醒对象和方式；不预设强提醒或自动赔付 |

营业时段决定“什么时候可以下单”，送达时限决定“已经下单后多久应送到”，两者必须分开。

不预设30／45／60分钟三档，不默认从下单起算，也不默认增加时效加价、楼层费、南海9栋费或快递满减。是否采用有关规则，须在定价与时限确认后明确。

## 4. 用户侧流程建议

### 4.1 业务入口

- 正常模式下，符合开放条件的华师南海用户可以选择“快递代拿”或“外卖代拿”。
- 两种业务使用清楚的名称和标识，避免误下单；快递现有入口、价格和规则保留。
- 其他校区不开放外卖入口，后端同样拒绝创建未开放校区的外卖订单。
- 审核模式下不新增外卖入口，保留原有页面文字、动作和金额保护；后端也须校验，不能只隐藏按钮。

### 4.2 已确认的取餐点

华师南海校区外卖下单提供以下5个取餐选项：

| 取餐点名称 | 归属 |
|---|---|
| 北门 | 校内 |
| 东南门 | 校内 |
| 阳光 | 校外 |
| 商业街 | 校内 |
| 您宿舍楼下 | 按用户宿舍地址定位，需显示具体楼栋 |

“校内／校外”记录取餐点归属，不直接套用快递的校内／校外价格；各取餐点是否同价，随外卖收费方案确定。

“您宿舍楼下”是取餐位置，不是新增的送达方式。建议使用用户当前收货宿舍地址并同步显示具体楼栋，避免骑手只看到“您”而不知到哪栋楼取餐。此选项是否默认送到门口、如何与“送到宿舍楼下／门口”组合，仍待确认；不因新增该选项擅自确定费用或时限。

### 4.3 外卖下单表单

建议表单保留以下信息，取餐识别信息的具体必填组合按各点实际取餐方式确定：

| 信息 | 作用 |
|---|---|
| 取餐地点 | 从北门、东南门、阳光、您宿舍楼下、商业街中选择；固定点显示校内／校外，宿舍楼下选项需显示具体楼栋，不能只填商家名代替实际位置 |
| 取餐凭证截图 | 沿用现有上传能力，展示外卖订单、取餐码等可核验信息 |
| 取餐识别信息 | 按取餐方式填写取餐码、柜号、手机号尾号等；避免无意义地全部要求必填 |
| 商家名 | 辅助识别，可按实际需要设为选填 |
| 送达地址 | 复用用户现有宿舍楼栋、房号和联系方式 |
| 配送位置 | 沿用“宿舍楼下／宿舍门口”的选择，具体收费待定 |
| 普通备注 | 选填，仅补充取餐和配送说明 |

不设置数量、尺寸、大单选项，也不要求用户重新填写已有收货资料。外卖平台来源不是首版必需字段，除非后续确认有实际用途。

### 4.4 提交及查看

用户核对取餐点、地址、已确定的收费和送达安排后，提交并支付代拿费。订单卡片、详情及客服入口明确展示“外卖代拿”，不能沿用“快递尺寸”“今天23点前”等不适用的文字。

价格或时限未配置完成时，不对外启用创建外卖订单的能力。

## 5. 骑手配送与取消流程

### 5.1 保留现有状态链

建议复用现有状态值和步骤，只对正常模式外卖订单调整业务显示文字：

```text
unpaid      waiting       accepted      picked       delivering      delivered      completed
待支付  →   待接单   →    已接单   →    已取餐  →    配送中      →   已送达    →   已完成
```

首版不合并或跳过 `picked`。现有后端严格校验 `accepted → picked → delivering → delivered`；保留状态链有利于复用操作、权限和记录。

### 5.2 接单与信息展示

- 骑手大厅能够区分快递与外卖，卡片突出取餐地点、送达楼栋、骑手收入及最终确定的送达安排。
- 复用骑手审核资格、校区隔离、不能接本人订单、接单上限及现有楼栋限制；不增加定位派单等新能力。
- 送上楼沿用南海现有同性限制和例外，不自行重写一套规则；前端展示与后端接单校验使用同一判定来源。
- 完整取餐码、截图、电话和房号沿用原权限保护，不能在公开待接单卡片或群发邮件中泄露。
- 确认送达继续要求上传凭证，用户可确认收货。首版建议沿用现有自动完成、观察期、结算和提现流程；如需为外卖调整，必须另行确认。

### 5.3 取消边界

| 订单阶段 | 用户侧处理 |
|---|---|
| 未支付 | 沿用现有取消与支付有效期处理 |
| 已支付、尚未接单 | 用户可按现有流程取消，退款按实际支付和优惠券使用情况处理 |
| 已接单、已取餐或配送中 | 用户不能自行取消，联系客服协商 |
| 已送达或出现争议 | 通过现有客服／售后入口核实处理，不自动取消或赔付 |

用户端隐藏取消按钮与后端权限校验必须一致。客服介入不等于一定取消或全额退款，不提前定义扣费、餐损赔付或骑手补偿规则。

### 5.4 新外卖订单邮件通知

**已确认需求：新外卖订单需要邮件通知骑手，内容与快递通知分开。** 这是新单通知，不是超时提醒；不等待订单超时才发。

建议沿用现有新单通知的触发边界与接收条件：

- 外卖订单支付成功并进入可接单的waiting状态后，通知华师南海本校区已通过审核且填写了接收邮箱的骑手；如果最终收费规则允许免支付订单，须在其成功创建并可接单后通知。
- 未付款、已取消、已被接走或其他不再可接的订单不发送过期的新单提醒；发送前核验状态。审核模式不发送此类外卖业务通知。
- 首版只通知华师南海骑手，不向石牌或广轻工跨校区群发。
- 复用现有邮件发送、通知去重和失败处理能力，按订单业务类型选择模板；不为外卖额外新建一套定时扫描，不直接套用很急快递的超时任务。
- 同一个新外卖订单不能同时触发快递模板和外卖模板。快递现有邮件的标题、正文和原有行为保持原样。

外卖专用邮件内容示意如下，金额和时间均为最终规则确定后写入订单的实际值：

```text
主题：[校园递小帮·外卖] 华师南海校区新外卖订单待接：{订单尾号}

华师南海校区有新的外卖代拿订单：{订单尾号}
取餐点：{北门／东南门／阳光／商业街及校内外归属，或“某栋宿舍楼下”}
送达楼栋：{宿舍楼栋}
配送位置：{宿舍楼下／宿舍门口}
骑手可得：¥{本单骑手收入}
送达要求：{本单已确定的送达时间或时限}

请打开小程序「骑手大厅」查看并接取外卖订单。
```

邮件不显示数量、尺寸或大单加价，也不包含完整取餐码、用户电话、房号或凭证截图。骑手需接单后按权限查看详细取餐信息。模板不得预填尚未确认的价格或30／45／60分钟档位。

选择“您宿舍楼下”时，邮件和骑手卡片需转为具体楼栋的客观表述，例如“7栋宿舍楼下”，不能直接写“您宿舍楼下”导致收件骑手误认为自己的宿舍；不展示用户房号。

## 6. 超时与异常处理

- **待接单超过送达截止时间不自动取消、不自动退款。** 待接单阶段用户主动取消权仍按原流程保留。
- 超时提醒单独讨论，不把快递现有“很急单等待30分钟无人接单，提醒运营”的任务直接套到外卖上。
- 是否展示倒计时、是否因超时额外通知骑手或客服、什么时候提醒，须在送达时限确定后设计；这些超时处理尚未确认，不影响已确认的新单邮件通知。
- 找不到外卖、柜码错误、取餐点信息不清时，复用联系用户和客服能力；不得为了结束任务直接标记送达。
- 错拿、洒漏、未收到或超时争议，保留取餐信息、送达照片与操作记录，交客服核实，不引入自动赔付或自动扣款。

未支付超时取消与“已支付但无人接单超时退款”是不同机制。保留前者不代表启用后者；未产生实付时也不存在现金退款，支付回调晚到等异常继续由现有支付安全流程处理。

## 7. 技术实现建议

以下是建议路线，尚未实施，不代表已经确定全部字段或数据库迁移。

### 7.1 共享订单主体，用类型区分

建议以现有 `orders` 为公共订单主体，新增明确的业务类型，例如：

```text
order_type：express／food
旧订单及旧请求默认表示express
```

这样可以继续复用订单编号、用户／骑手关联、支付、退款、售后、收入、经验及转单记录，避免另建一整套独立外卖资金体系。

外卖专用信息可使用少量新增字段，或通过与订单一对一关联的详情表保存；两种组织方式在参数定稿后选择。外卖详情附表不等于另建完全独立的订单和结算系统。

### 7.2 最小数据需求

| 数据 | 建议处理 |
|---|---|
| 业务类型 | 明确标识快递／外卖，所有相关接口和查询按需处理 |
| 取餐地点 | 保存选定点位、名称及适用的校内／校外归属快照；首版为北门、东南门、阳光、您宿舍楼下、商业街。宿舍楼下属于动态点位，还须保存取餐楼栋快照，不能因用户之后修改资料而改变历史订单取餐位置 |
| 取餐识别信息 | 按权限保存取餐码、柜号等实际需要的内容 |
| 凭证 | 复用现有上传与订单附件关联能力，明确隐私权限 |
| 金额及骑手收入 | 后端计算并保存建单快照，不能信任前端提交金额 |
| 送达规则与截止时间 | 根据最终确认的规则保存必要快照；如使用deadline_at，不得在支付、接单、转单时随意重置 |
| 普通备注 | 尽量复用现有note，不为份数或大单另增JSON字段 |

不必预先增加 `food_details_json`、份数、尺寸或大单收费字段。不要把外卖伪装为现有 `urgent` 快递单，以免误套快递加急价、时限、筛选及邮件逻辑。

### 7.3 旧版小程序兼容

- 历史订单和缺少业务类型的旧请求保持快递语义；未知业务类型应拒绝，不能误落入另一业务。
- 新包明确支持外卖后才获取和操作相应业务。旧版大厅、订单列表、首页当前单等展示接口不能把外卖单当快递下发。
- 用户／骑手操作接口按业务类型、客户端能力和真实权限校验，不能仅靠前端隐藏入口或筛选。
- 支付回调、退款及结算属于服务端资金流程，应正确识别真实订单，不能因为回调没有客户端能力参数而被阻断。
- 管理台需要先具备识别和处理外卖订单的能力，再开放真实外卖下单。

### 7.4 独立业务参数，保留现有快递规则

- 外卖开放开关、取餐点、价格和营业时段建议按校区配置，首版只允许 `nanhai` 开启。
- 快递的07:30–20:00后端建单窗口、已有定价和时限保持原样。现有建单接口的时间判断需按业务区分，不能为了外卖直接放宽全部订单。
- 审核模式和平台总暂停服务等既有保护继续生效；外卖单独开关不能绕过这些保护。
- 价格版本、报价核验、优惠、收入及历史快照均需核对适用业务。复用计算工具不等于自动套用现有快递收费政策。
- `platform_settings` 当前按校区组织；如在原表扩展外卖字段或新增专用配置，应先确定结构，不直接新增与既有校区读取假设冲突的“价格行”。

### 7.5 管理台与公共流程检查

订单列表／详情增加清晰的业务类型及相应取餐信息，支持按类型筛选。公共金额汇总不得漏计或重复计入外卖收入；涉及支付回调、退款、优惠券、骑手收入、售后、经验、转单和通知的地方，都需逐项核对类型适配，不能认为加一个字段后自然全部兼容。

如有数据库变更，按项目规范维护迁移与 `schema.sql`；新增表须加入重置脚本清单和相关清理顺序，但不得因此运行重置或重复执行历史迁移。

## 8. 对原讨论稿的现状纠正

| 原稿表述 | 当前源码事实 |
|---|---|
| waiting超过deadline_at自动取消退款 | 此机制已移除；当前不自动取消已支付待接单订单，本次也不新增 |
| urgent按接单后1小时计算 | 真实截止按下单后1小时计算，接单不重置；部分旧展示文案不等于实际计时 |
| 快递接单后用户也可自行取消 | 用户只能自行取消unpaid／waiting；已接单需联系管理员，本次外卖沿用这一边界 |
| settled是订单状态值 | 结算主要由settled_at等字段及骑手余额体现，不应新增或假设已有settled订单状态 |
| commission_rate是orders现有字段 | 目前来自校区设置，建单时保存计算后的rider_income；字段设计须按实际schema核验 |
| 外卖可以直接跳过picked | 当前状态接口会拒绝跳步，首版建议保留现有状态链 |
| urgent-alert已经支持送达前通知骑手／客服 | 现机制是很急快递待接30分钟的运营邮件，不是外卖送达前提醒 |

## 9. 实施顺序与验收清单

1. **需求定稿**：在已确认的5个取餐选项基础上，补齐价格、送达时限及计时起点，明确营业时段和优惠／收入口径；确认是否需要首版超时提醒，宿舍楼下及其他取餐点的特殊要求按实际补充。
2. **细化设计**：确定业务类型、外卖字段组织、旧包能力识别、权限、价格及时间配置方案，列出公共流程适配清单。
3. **后端与管理台**：完成必要迁移、类型分流、服务端校验和管理台识别，外卖开关保持关闭。
4. **小程序**：正常模式南海入口、精简表单、订单／骑手展示和原配送流程适配；审核既有文字和动作保留。
5. **检查和部署**：按项目规范备份、回归、构建和部署；不创建未经授权的真实订单，不切生产审核模式做验证。
6. **上线试行**：负责人自行上传／提审／发布小程序，在新客户端和实际取餐流程验证后，仅开启南海外卖业务。

重点验收：

- 原快递计价、时限、取消、接单、支付、退款、结算和提现回归不变。
- 其他校区及审核模式无法通过直接调用绕过外卖开放限制。
- 旧客户端仍可使用快递，不误展示或操作外卖订单；资金回调不受客户端版本识别影响。
- 外卖没有数量、尺寸或大单加价；金额和截止时间符合最终确认规则并保存快照。
- 已接单用户无法自行取消，客服及送达凭证权限正确。
