## 2. 修改与部署约束

- 动手前说明改动范围，保留无关工作和图片。源码是开发入口，不从旧构建包继续改。
- 小程序修改后运行 `npm run validate`、相关回归和 `npm run build:prod`；负责人用新产物验证、发布。
- 后端变更核对线上基线、备份、`node --check`，部署后重启对应 PM2 进程并检查 `/health`。切换 release 后核验 PM2 实际脚本与工作目录；`pm2 reload` 不保证更新路径。
- 管理台是静态站，部署实际改动的 JS/CSS/HTML 等文件；改 `api.js` 就必须同步该文件。线上备份放 Web 根目录外，部署后浏览器强刷。
- `/health` 成功不等于数据库认证或全部业务正常；相关变更还需验证实际查询和关键行为。
- 生产写操作需要对象核验、私有备份、事务/前置断言、审计和回读。不得为测试随意切生产审核模式、建真实订单或清理真实用户。
- 历史迁移不要重跑。新增表同时维护 `schema.sql`、迁移和 `server/scripts/reset-data.js` 清单；订单子表还要更新清理顺序。
- 数据库统一 UTC；资金/结算时间判断优先 SQL 比较，北京自然日统计与 UTC 存储区分。纯日期账目按 `YYYY-MM-DD` 读写。

## 3. 多校区与价格

前端 `config/constants.js`、后端 `server/src/campus-config.js` 与管理台校区配置保持一致；楼栋校验、格式化、性别、取件点和价格规则都要传 campus，不能默认所有数字楼栋都是南海。

| 校区 | 地址与接单特征 |
|---|---|
| 南海 | 1–9 栋及 25 号楼；送上楼通常受同性规则约束，9 栋豁免；混宿与未填骑手性别按现有规则处理 |
| 石牌 | 配置白名单楼栋 + 自由房号；送上楼限本栋，楼下自取可跨栋；不标楼栋性别 |
| 广轻工 | 1–48 栋，9–24 为女生楼、其余男生楼；送上楼受同性规则约束，无南海 9 栋收费/性别豁免 |

具体白名单与楼层细分以代码配置为准。石牌大厅展示楼栋，接单前隐藏房号等敏感信息。

- 前端下单入口 08:00–20:00；后端真实窗口 07:30–20:00；今天档送达23:00前。新稍急/很急为下单后4h/1h，稍急晚间可超过23:00（§14），下单窗口不变。
- 南海基础价：小件校内/外 1/2，中件 3/4，大件 5/6；很急整单 +4；9 栋固定 +0.5，门口费另计。新版 V3 将件小计及全部附加费合计凑满减，旧包 V2 保留仅件小计口径（§12）。
- 各校区读取自己的 `platform_settings`；不能把南海楼栋费、石牌驿站价照搬其它校区。抽成当前为南海 10%、石牌 10%、广轻工 20%。
- 服务端金额用整数分计算。V2/V3 请求提交对应 `pricingVersion`、`quotedTotal`，服务端按协议独立重算并拒绝不一致报价；客户端不能决定实扣金额。
- 历史订单金额、抽成及骑手收入均按建单快照，不回填重算；改价只影响新单，并处理价格缓存版本。
- `toDoor` 与后端 `noUpstairs` 语义相反，转换中的取反不能随意删。
- 南海 `campus_7` 是校内取件点；整单汇总先归一为 campus，单件仍保留具体点位。石牌按驿站筛选，其它校区按校内/校外筛选；切校区重建筛选器。
- 优惠券按校区过滤/校验，NULL 表示通用；转区后旧券仍属原校区。新注册不再自动发历史 2 元新用户券。

## 4. 订单、骑手、支付与收入

- 接单大厅展示本校区已支付 waiting 订单，不能接的置灰并显示原因。大厅与 accept 共用后端 `evaluateOrderGrab`，前端不能维护另一套授权逻辑。
- 服务端检查未支付、自接单、转单禁接期、本栋/性别等条件；跨校区和未支付订单不进入接单池。
- 转单仅允许 `accepted`，2h 内不能接回、每天最多 3 次。锁顺序为骑手 → 订单 → 通知；转单重置扣留收入标记及必要的紧急邮件队列。
- 确认送达至少一张凭证，客户端与服务端均校验。送达后 12h 自动完成；观察期及隐私隐藏时间独立。accepted/picked/delivering 不因跨日自动结束。
- 支付为 XorPay 原生二维码：保存图片后微信扫一扫，再返回小程序。零元券单取消只退券，不建现金退款。
- 隔日退款受微信当天未结算余额影响；`manual_review` 不会自动补退，需核对实际退款和凭证，防重复操作。
- 骑手提现为线下打款、平台记账，审批后异步结清邮件；邮件失败仅记录，不代表资金到款失败或成功。
- 骑手收入按优惠券前、已扣满减的原价及当时抽成快照计算；券损由平台承担。
- 订单净收入为 `SUM(paid_amount) - SUM(IF(withhold_rider_income=1, 0, rider_income))`，排除 unpaid/cancelled。扣留骑手收入会增加平台份额，不能当成订单贡献为零。
- 明细「实际净收入」=订单口径净收入+额外收支。概览今日卡片含当日额外收支，14 天折线/明细「净收入」列保持纯订单口径。

## 5. 注册、资料与转校区

- 正常注册使用普通校区入口和选择弹窗；未选校区提交也弹出列表并保留输入，选后须核对楼栋。原先正式版入口消失的最初原因没有复现，不应断言全因旧版本。
- 空楼栋显示「请选择宿舍楼」，正常 picker 真实楼栋索引后移；不能视觉默认第一栋但提交仍为空。审核原索引/文字保留。
- 用户手机号与骑手手机号是独立资料；昵称、姓名备注、真实姓名也应区分。
- `POST /mini/campus-change-requests` 校验通过立即 approved；普通用户需无本人未结束订单，骑手还需无未结束配送任务。
- `disputed` 且至少存在一条售后、所有售后均 resolved 可视为结束；无售后/部分未结案仍阻止。只调整转区资格，不修改订单状态、收入或观察期。
- 事务内同步 users/riders 校区、迁移待审骑手申请、清空旧地址并保留请求历史。骑手审批也要防止沿用旧申请校区。
- `register`、`PUT /me` 不能绕过转区约束；旧客户端能提交即转成功，但可能仍显示旧等待文字或旧资料，需刷新。
- 人工改校区审核菜单及管理 API 已移除；保留用户提交/历史接口、请求表和骑手审批依赖的锁函数。
- 为注册测试重置账号应先核对订单/骑手等关联并备份审计；清客户端缓存可防旧资料自动登记。用户主动新注册成功后要保留该新账号，不要继续按旧清理目标循环删除。

## 6. 审核模式与防闪

`review_mode` 是全平台展示开关，作用于所有校区及实际用户。管理端开关操作需要相应角色与审计；不能只修改单个校区行，也不要为验证实际翻转生产值。

审核开启时，各校区使用既有登记/办理文字，隐藏价格、支付、钱包、优惠券及相关金额；正常模式保留正常功能。风格可以共用最新 UI，普通功能修改须保持审核文字和操作。

模式只由独立设置核验结果更新；普通首页/下单响应或离线旧缓存不得覆盖全局。热刷新保持本次会话已确认值，失败也不自行跳审核；冷启动未知仍采用金额保护。服务器实际返回不同模式后才切换，不承诺所有停留客户端瞬时同步。

保留 `scripts/validate.js` 的收入、注册和订单语义守卫，以及 `scripts/test-review-mode.js` 的三校区、冷/热启动、缓存、模式变化、晚到支付和生命周期回归。审核自动登记缺 campus 已按 §16 修复，新包微信侧验证仍见 §10。

## 12. 附加费参与满减（2026-10-20）

- 新版 V3 使用 `件小计 + 加急费 + 门口费 + 楼栋费` 凑满减，按当前校区配置只取最高一个达标档，满减后再抵扣优惠券。默认仍为满5减0.5、满10减1、满20减3；单件达到金额也适用，不按门槛倍数重复减。
